## [crustc：将 Rust 编译器翻译为 C 以支持陌生硬件和引导](https://github.com/FractalFir/crustc) ⭐️ 8.0/10

crustc 项目将整个 Rust 编译器（rustc）翻译为 C 语言，这是历时三年的第 14 次尝试。生成的 C 代码使 Rust 能在缺少 LLVM 或 GCC 后端的平台上编译，并有助于编译器引导。 这项工作让 Rust 能在缺乏 LLVM 的极度陌生或老旧硬件上运行，并解决了引导困境——构建 rustc 通常需要现成的 Rust 编译器。它拓展了 Rust 的适用范围，并可能增强对编译器供应链的信任。 该方法使用转译器将 Rust 源码转为 C，再借助 GCC 进行优化；编译器实现尚未公开发布。作者提到的第 14 次尝试凸显了此类翻译的难度。

hackernews · Philpax · 7月2日 22:57 · [社区讨论](https://news.ycombinator.com/item?id=48768464)

**背景**: 编译器引导是指从源码构建编译器的过程，通常需要该语言的旧版编译器，这构成了先有鸡还是先有蛋的问题。Rust 官方编译器本身用 Rust 编写，引导需要已有的 Rust 编译器；转译为 C 后，可以仅从 C 编译器开始引导。许多陌生硬件平台没有 LLVM 支持，因此 C 后端提供了替代的编译路径。

## [Linux 6.9 回归缺陷：LUKS 挂起时未能从内存中擦除加密密钥](https://mathstodon.xyz/@iblech/116769502749142438) ⭐️ 8.0/10

在 Linux 6.9 中，一个内核回归导致 LUKS 挂起（suspend）功能不再在挂起到内存时从 RAM 中擦除主加密密钥，而此前该功能可安全清除密钥。 这一回归缺陷削弱了依赖 LUKS 挂起功能在睡眠期间保护密钥的系统安全性，拥有物理访问权限的攻击者可能提取密钥。 该缺陷具体影响 `cryptsetup luksSuspend` 机制，通常通过自定义 initramfs 脚本（如 Debian 的挂起脚本）实现，仅影响主动使用此功能的系统。目前已添加测试以避免未来再次破坏。

hackernews · IngoBlechschmid · 7月2日 15:25 · [社区讨论](https://news.ycombinator.com/item?id=48763035)

**背景**: LUKS（Linux 统一密钥设置）是 Linux 上磁盘加密的标准，基于 dm-crypt。正常运行时，主密钥留存于内核内存中以实时解密数据。`luksSuspend` 命令可临时停用加密设备并从内存中擦除密钥，以减少攻击窗口，通常用于系统挂起前。该功能并非普遍使用，常由 Debian 等发行版通过自定义脚本提供。

## [Postgres 事务：分布式系统的超能力](https://www.dbos.dev/blog/co-locating-workflow-state-with-your-data) ⭐️ 8.0/10

文章提出将工作流状态与应用程序数据共同放置在 Postgres 中，利用数据库事务确保工作流步骤和数据变更的原子性，无需独立的消息队列。 这种方法通过消除发件箱模式的复杂性并减少潜在故障点，简化了可靠分布式工作流的构建，使开发者能更轻松地保持业务逻辑与状态转换之间的一致性。 每个工作流步骤对应一个数据库提交单元，这固有地将工作流引擎与数据库耦合。这种紧密集成可能使得未来的分离变得复杂，但提供了即时的简洁性。

hackernews · KraftyOne · 7月2日 18:38 · [社区讨论](https://news.ycombinator.com/item?id=48765639)

**背景**: 在分布式系统中，发件箱模式通常用于通过在同一事务中将消息写入特殊表，然后依赖单独的转发进程，来实现原子地更新数据库和发送消息。这增加了基础设施和复杂性。本文的策略则让工作流引擎直接操作事务状态，绕过了对发件箱的需求。
