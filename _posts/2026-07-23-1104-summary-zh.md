## [陶哲轩用 ChatGPT 探查雅可比猜想反例。](https://chatgpt.com/share/6a5fdc7a-d6f8-83e8-bbea-8deb42cfed56) ⭐️ 8.0/10

一段共享的 ChatGPT 对话显示，数学家陶哲轩通过一系列有针对性的提示和化简，考察一个声称的雅可比猜想反例。这个内容并不是经过同行评审的证明，但它记录了专家主导使用 LLM 参与高等数学推理的一个罕见案例。 如果这个雅可比猜想反例最终被验证为真，它将成为代数几何和多项式映射理论中的重大结果。即使不考虑数学结果本身，这段对话也很重要，因为它展示了顶尖专家如何把 LLM 当作交互式推理辅助工具，而不是最终权威来源。 讨论指出，这个所谓反例似乎具有特定的代数结构，而不是盲目暴力搜索得到的构造。主要限制在于，共享对话可能包含错误或未经验证的步骤，因此这个数学主张仍然需要独立核查和正式表述。

## [GigaToken 加速大模型分词。](https://github.com/marcelroed/gigatoken/) ⭐️ 8.0/10

marcelroed 在 GitHub 上发布的 GigaToken 声称可以以每秒数 GB 的速度进行语言模型分词，并在某些对比中达到约 1000 倍于常见分词器实现的吞吐量。它的核心做法包括基于 SIMD 的预分词、激进缓存以及减少底层开销。 分词在大模型技术栈中常被视为基础管道，但更快的分词对数据集准备、大规模预处理、批处理以及需要处理海量文本的流程可能很重要。对于普通推理服务来说，影响可能有限，因为分词通常只占总推理时间的很小一部分。 该项目称其支持广泛的 CPU 硬件以及几乎所有常用分词器，并特别强调对常见 BPE 分词器的支持。它的主要技术思路是用经过 SIMD 优化的代码替代严重依赖正则引擎的预分词，减少分支和 Python 开销，并缓存重复预分词片段的映射。

hackernews · syrusakbary · 7月22日 17:20 · [社区讨论](https://news.ycombinator.com/item?id=49010167)

**背景**: 语言模型分词会把文本转换成模型可以处理的整数标记。许多现代分词器使用 BPE，它会根据高频出现的字节或字符序列构造标记。预分词是在应用分词器合并规则之前，把原始文本切成片段的早期步骤，通常由正则表达式实现。SIMD 指单指令多数据，可以让 CPU 并行处理多份数据；如果实现得当，它能显著加速文本扫描类任务。

## [开发者应该理解 SIMD。](https://mitchellh.com/writing/everyone-should-know-simd) ⭐️ 7.0/10

Mitchell Hashimoto 的文章《Everyone Should Know SIMD》认为，SIMD 是开发者应该理解的实用性能工具，而不是晦涩的底层技巧。相关讨论重点关注编译器何时能成功自动向量化代码，以及何时会悄悄退回到标量执行。 SIMD 可以显著提高对大量数据元素执行同一操作的工作负载吞吐量，因此它与系统编程、游戏、媒体处理、数值计算和其他性能敏感软件密切相关。理解 SIMD 还能帮助开发者写出更容易被编译器优化的代码，而不是假设编译器总能自动找到最快实现。 一个关键限制是，自动向量化很脆弱：依赖数据的分支、别名问题、不规则内存访问或不合适的数据布局都可能阻止编译器生成 SIMD 代码。多位评论者强调，在使用显式 SIMD 内建函数或库中的向量函数之前，应先查看编译器优化报告并改进数据布局。

hackernews · WadeGrimridge · 7月22日 17:48 · [社区讨论](https://news.ycombinator.com/item?id=49010648)

**背景**: SIMD 的意思是“单指令多数据”，是一种并行计算模型，即一条指令同时对多个数据点执行同一种操作。现代 CPU 通过指令集提供 SIMD 能力，使合适的循环和数组式计算能够在一条指令中处理多个值。编译器有时可以从普通代码自动生成 SIMD，但开发者通常需要以有利于向量化的方式组织数据和控制流。

## [初创公司获得一份 Postgres 生存指南。](https://hatchet.run/blog/postgres-survival-guide) ⭐️ 7.0/10

Hatchet 发布了一篇面向初创公司的指南，介绍如何应对生产环境中的 PostgreSQL 问题，重点是实际运维而不是新的数据库功能。相关 Hacker News 讨论补充了关于 UUIDv7、确定性锁顺序、查询计划、备份、ORM、JSONB 和模式设计的修正与扩展。 PostgreSQL 是许多初创公司的默认数据库选择，但很多故障来自运维短板，例如不安全的迁移、锁竞争、缺少备份以及模式约定不清。这样一份简明的生存指南可以帮助小团队在拥有专职数据库可靠性工程师之前减少宕机风险。 评论者强调，减少被锁定的行数还不够；查询应按确定性顺序获取锁，例如按 id 升序，以降低死锁风险。他们还认为任何生产环境清单都应包括经过测试的备份和恢复方案，并讨论了级联删除、ORM、自增主键、追加式数据模型以及谨慎使用 JSONB 等取舍。

hackernews · abelanger · 7月22日 12:36 · [社区讨论](https://news.ycombinator.com/item?id=49005787)

**背景**: PostgreSQL 使用 MVCC 和显式锁等机制来控制对表和行的并发访问。当多个事务读写同一批数据时，锁对于保证正确性是必要的，但顺序不当或范围过大的加锁可能导致阻塞或死锁。EXPLAIN 等工具可以帮助开发者查看 PostgreSQL 准备如何执行查询，因为实际执行计划会影响性能和加锁行为。
